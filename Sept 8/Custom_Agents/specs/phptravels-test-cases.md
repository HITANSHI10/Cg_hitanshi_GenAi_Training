# PHPTRAVELS Test Cases

This document is a separate test-case artifact derived from [specs/phptravels-test-plan.md](phptravels-test-plan.md). It is intended for QA execution and automation planning.

| Test ID | Scenario | Preconditions | Steps | Expected Result | Priority | Automation |
| --- | --- | --- | --- | --- | --- | --- |
| TC-001 | Home page loads with demo notice and public navigation | User opens the public PHPTRAVELS site | 1. Open the home page. 2. Check the brand, booking options, login/signup links, and menu. 3. Locate the demo notice. | Page loads correctly; brand and primary booking options are visible; demo notice clearly states simulated pricing and sandbox payments. | P0 | Yes |
| TC-002 | Header and footer navigation links work | User is on the home page | 1. Click each major navigation item. 2. Check destination pages and footer support links. 3. Validate currency/language selectors. | All visible public links open valid destinations and the site remains navigable. | P0 | Yes |
| TC-003 | Valid stay search succeeds | User is on the stays search screen | 1. Enter destination, check-in date, check-out date, occupancy, and nationality. 2. Submit the search. | Search is accepted and results display or a proper empty state appears. | P0 | Yes |
| TC-004 | Stay search blocks incomplete input | User is on the stays search form | 1. Leave destination blank. 2. Remove dates or nationality. 3. Submit the form. | Validation error is shown and submission does not continue silently. | P0 | Yes |
| TC-005 | Stay search rejects invalid date range | User is on the stays search form | 1. Set check-out equal to or before check-in. 2. Submit. | The form shows a clear validation message and prevents invalid search. | P0 | Yes |
| TC-006 | Stay results display available property information | Valid stay search has already been submitted | 1. Review result cards. 2. Verify name, location, rating, price, image, and details link. 3. Open one property. | Each result includes expected details and the property detail page opens correctly. | P0 | Yes |
| TC-007 | Unavailable stay search shows no-results state | User knows the chosen destination has no inventory | 1. Search for an unavailable destination. 2. Observe the displayed state. | A clear no-results message is shown without fake success indicators. | P1 | Yes |
| TC-008 | Flight search accepts valid input and shows comparison results | User is on flight search | 1. Enter departure city, arrival city, dates, and passenger count. 2. Submit. 3. Apply sort/filter if available. | Flight fares appear and filtering/sorting updates the listing without losing core search data. | P0 | Yes |
| TC-009 | Flight search validates missing values | User is on flight search screen | 1. Submit partial or blank flight search data. 2. Review validation. | Validation prevents silent submission and shows helpful guidance. | P1 | Yes |
| TC-010 | Booking review page shows summary and optional extras | User has selected a valid hotel/flight | 1. Continue to review. 2. Confirm summary details. 3. Check for optional extras like insurance or car add-ons. 4. Continue without email when required. | Summary page is shown; extras are clearly offered; required email is validated. | P0 | Yes |
| TC-011 | Traveller details validation works for one and multiple travellers | User is on checkout traveller details | 1. Enter valid single traveller data. 2. Add multiple travellers and leave one incomplete. 3. Submit malformed or blank values. | Valid data proceeds; incomplete or invalid entries are blocked with actionable validation. | P0 | Yes |
| TC-012 | Valid sandbox payment succeeds | User is at the payments page | 1. Verify sandbox payment methods are shown. 2. Accept terms. 3. Submit valid sandbox payment data. | The booking completes successfully and reaches a confirmation page without requiring real card credentials. | P0 | Yes |
| TC-013 | Invalid or declined sandbox payment is rejected safely | User is at the payment step | 1. Submit declined/cancelled/invalid payment data. 2. Observe the error state. | The user sees a recoverable failure and the system does not display a false success page. | P0 | Yes |
| TC-014 | Confirmation page displays booking result and delivery notice | Valid payment has completed | 1. Open the confirmation page. 2. Check booking reference, summary, and notification text. | Confirmation page clearly shows success and notes that email delivery may follow. | P0 | Yes |
| TC-015 | Customer login and signup validation works | User is on authentication screens | 1. Open customer login. 2. Submit empty or invalid values. 3. Open customer signup and submit valid synthetic data. | Validation prevents bad input; valid user flows proceed as supported. | P1 | Yes |
| TC-016 | Agent signup validates registration data | User is on agent registration page | 1. Open agent signup. 2. Submit invalid or blank info. 3. Submit valid synthetic registration info. | Invalid data is rejected; valid data is accepted when the flow supports it. | P1 | Yes |
| TC-017 | Visa booking form validates required data | User is on visa booking entry | 1. Open visa flow. 2. Pick a visa option if available. 3. Submit incomplete details. 4. Try an unavailable service. | Required fields are validated and unavailable service states are handled with a clear explanation. | P1 | Yes |
| TC-018 | Support and policy links are reachable and valid | User is on the public site | 1. Open support/contact pages. 2. Test email, phone, WhatsApp, and social links. 3. Open policy pages. | Links resolve correctly and the required support/policy information is accessible. | P1 | Yes |
| TC-019 | Refund policy clearly explains eligibility and request requirements | User is on refund/cancellation page | 1. Open policy content. 2. Review refundable, partially refundable, and non-refundable guidance. 3. Attempt a refund request with missing data. | Policy content is explicit and refund requests require required information before submission. | P1 | Yes |
| TC-020 | Mobile and desktop responsive behavior remains usable | User changes viewport sizes | 1. Open site on desktop. 2. Resize to mobile width. 3. Open mobile menu. 4. Navigate by keyboard only. | Core flows remain usable across viewport sizes, and keyboard navigation works. | P1 | Yes |
| TC-021 | Accessibility labels and validation messages are usable | User interacts with main forms | 1. Trigger validation. 2. Review button names and messages. 3. Check accessible labels and alt text on images. | Form controls are identifiable and validation feedback is clear and readable. | P1 | Yes |
| TC-022 | Authentication errors do not leak sensitive information | User is on login/signup screens | 1. Submit invalid data for both existing and non-existing accounts. 2. Observe error messages. | The system does not reveal whether an account exists or leak sensitive details. | P1 | Yes |

## Notes

- This file is derived from the plan and is intended for direct QA use.
- Some scenarios may require environment-dependent or supplier-dependent controls such as actual availability or payment results.
- Because the site is a demo environment, tests should avoid real card data and production account data.
